PRISM SECURITY AUDIT — CODEX PERSISTENT INSTRUCTIONS / STATUS

Purpose:
Maintain a persistent, authoritative security-audit status for the PRISM repository. This status must survive context changes and prevent completed findings from being re-audited unnecessarily or pending findings from being accidentally skipped.

GENERAL RULES
1. Treat this file/instructions as the source of truth for audit progress unless a newer explicit audit report supersedes it.
2. Never claim a finding is fixed or closed without evidence from:
   - regression tests,
   - relevant broader test suites,
   - diff/worktree inspection,
   - and an independent closure review where required.
3. Preserve the distinction between:
   - VALIDATED / CONFIRMED
   - REMEDIATION IN PROGRESS
   - FIXED / READY FOR CLOSURE
   - CLOSED / INDEPENDENTLY VERIFIED
   - NOT CONFIRMED
   - PENDING VALIDATION
4. Do not modify unrelated pre-existing working-tree changes.
5. For each finding, work one finding at a time:
   VALIDATE -> RED TESTS -> FIX -> GREEN TESTS -> ALTERNATE-PATH REVIEW -> INDEPENDENT CLOSURE REVIEW.
6. Do not silently reopen a CLOSED finding because of an unrelated observation. Create/track a separate finding unless the new issue directly defeats the closed security property.
7. Keep exact test baselines from the relevant audit report. Do not assume one universal integration-test count.

F-13 — Password-reset token replay / existing sessions survive password reset
Original severity: P2
Status: PENDING VALIDATION
Suspected:
- OTP creates short-lived reset JWT.
- Reset token may remain reusable until expiry.
- Existing seven-day access JWTs may remain valid after password reset.
Must empirically test token replay and post-reset session validity without weakening production auth.

F-13 STATUS UPDATE — 2026-09-24
Previous status: PENDING VALIDATION
New status: FIXED / READY FOR CLOSURE (CONFIRMED)
Severity: P2 (account-takeover persistence: a reset does not evict an attacker's sessions).
What was proven (RED, 4 cases, OTP captured from mocked email):
- Reset token replay: the same 5-minute reset token set a second password (200).
- Sessions survive reset: a 7-day session issued before the reset still passed
  authenticate afterwards (no password-change/version check anywhere).
- NEW (found during validation): the reset token is signed with JWT_SECRET and carries
  userId, and authenticate() never checked `purpose` — so the reset token itself worked
  as a login session (GET /api/auth/me 200).
- An older reset token still worked after a newer reset completed.
- reset-password is the only password writer for users (no change-password route, no
  server-side logout); super_admins have no reset flow.
Fix:
- users.token_version INT NOT NULL DEFAULT 0 (init.sql). Session JWTs (login, register,
  invite-accept) carry `tv`; authenticate() rejects `tv` mismatch with 401
  SESSION_REVOKED. Tokens without `tv` (pre-existing sessions) count as version 0, so no
  one is logged out by the deploy itself.
- authenticate() rejects any token carrying `purpose` (SESSION_INVALID).
- Reset tokens signed with a separate key (JWT_SECRET + ":password-reset") and bound to
  `tv`; reset-password does UPDATE ... SET token_version = token_version + 1 ... WHERE
  id = $2 AND token_version = $3 — atomic single use, kills all older reset tokens and all
  sessions; also clears reset_otp fields.
- Session-death 401s from authenticate carry code SESSION_INVALID / SESSION_REVOKED
  (the no-Authorization-header 401 body is unchanged — F-04 test asserts it exactly).
- Frontend: apiFetch dispatches auth:session-expired only for those codes (a wrong vault
  PIN or delete-company password 401 does not sign out); App shows a "Signed out" dialog
  with "Log in again". This also fixes the pre-existing behaviour where an expired 7-day
  token left the user stuck on error messages.
Files: init.sql, api/src/routes/auth.js, api/src/middleware/auth.js, web/src/api/client.js,
  web/src/App.jsx, api/src/__tests__/integration/f13PasswordResetSessions.test.js (new, 7).
Regression: F-13 7/7 (4 RED before). auth, users, securityHardening, marketplace x2 (F-03/
  F-04), f10, settings, superadminAiProvider: all green (37/37 on final rerun of the
  auth-touching set; 82/83 before restoring the F-04 exact 401 body). Unit 1739 passed /
  7 skipped. Web build passes.

AUDIT PROCESS FOR EVERY PENDING FINDING

Phase 1 — Validation
- Read the relevant route/helper/schema/database code.

Phase 2 — Remediation
Only after confirmation:
- Propose the smallest safe fix.
- Preserve legitimate frontend/API behavior.
- Implement regression tests for every confirmed attack path.
- Avoid touching unrelated files or pre-existing dirty worktree changes.

Phase 3 — Verification
- Run dedicated regression suite.
- Run relevant existing targeted suites.
- Run full unit suite.
- Run integration suite and compare exact failures to baseline.
- Search for alternate mutation/read paths.
- Inspect git diff.
- Confirm no unrelated files were changed.

A separate review must challenge the fix:
- Reproduce original exploit attempts.
- Search for sibling/alternate routes.
- Test tenant boundaries and role boundaries.
- Verify downstream side effects.
- Confirm frontend compatibility.
- Confirm no test was weakened.
- Only then mark CLOSED.
